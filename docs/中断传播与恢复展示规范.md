# 中断传播与恢复展示规范

## 1. 目标

本文档定义 Web 前端最终应展示的中断传播与恢复策略结果、数据来源和解释口径，确保：

- 前端与后端完全分离。
- 前端只消费稳定的数据接口文件，不依赖 Python 内部对象。
- 供应传播、需求传播、融合结果、恢复策略的展示口径一致。
- 图表、表格、指标卡、快照图的含义可以被审计和复核。

## 2. 前后端分离原则

### 2.1 基本原则

- 后端负责仿真、汇总、导出。
- 前端负责读取导出文件并展示，不参与业务计算。
- 前端不得直接依赖 Python 类、函数、临时内存对象或内部状态树。
- 前端展示所需的结构化数据以 `CSV` 为主，图片仍以 `PNG` 为主。

### 2.2 当前导出约定

单次运行结果目录下：

- `tables/`：仿真原始表和汇总表
- `tables/frontend/`：前端展示专用 CSV 接口
- `figures/`：趋势图、路径图、月度图等
- `network_snapshots/`：关键时点网络快照
- 不再输出前端兼容性 `JSON` 汇总

前端推荐优先读取：

- `tables/frontend/*.csv`

前端只消费 `tables/frontend/*.csv` 与 `artifact_paths.csv` 中声明的图片资源路径，不再依赖兼容性 `JSON`。

## 3. 前端展示数据接口

### 3.1 前端专用 CSV 目录

目录：`tables/frontend/`

应包含以下数据集：

- `scenario.csv`
  - 当前场景基础信息
- `summary.csv`
  - 单次运行的一行汇总
- `kpis.csv`
  - 首页 KPI 卡片使用的一行数据
- `policy_start_snapshot.csv`
  - 恢复策略开始生效日关键指标
- `time_series.csv`
  - 日级业务与供给 KPI 趋势
- `network_time_series.csv`
  - 日级网络节点/边统计趋势
- `network_markers.csv`
  - `t0 / t_start / t_supply_peak / t_policy_start / t_recovery`
- `top_impacted_paths.csv`
  - 关键影响路径表
- `policy_events.csv`
  - 恢复策略事件时间线
- `artifact_paths.csv`
  - 图片和补充产物路径
- `manifest.csv`
  - 前端数据集清单

### 3.2 设计含义

- `tables/` 里的 CSV 更偏“分析与审计”
- `tables/frontend/` 里的 CSV 更偏“直接给页面组件消费”
- 两套可以共享底层字段，但用途不同

## 4. 最终页面应展示什么

### 4.1 页面一：场景总览

展示内容：

- 场景名称、目标对象、开始日期、持续天数、严重度
- `ttr_days`
- `affected_days`
- `failed_days`
- 平均服务水平
- 平均系统服务水平
- 传播停止日期
- 恢复策略总成本
- 预计中断损失

推荐数据源：

- `scenario.csv`
- `summary.csv`
- `kpis.csv`

展示内容：

- 供应商中断/降级趋势

- 物料、装配、产品的受影响/阻断趋势
- 月度中断节点分布
- 传播时长对比

推荐数据源：

- `time_series.csv`
- `network_time_series.csv`
- `network_markers.csv`
- `artifact_paths.csv`

推荐图片：

- `supplier_network_trends.png`

- 替代导致的需求转移

推荐数据源：

- `time_series.csv`

### 4.4 页面四：恢复策略与恢复过程

推荐数据源：

- `policy_events.csv`

- 策略开始执行日网络
- 恢复日网络
- 场景起始网络

推荐数据源：

- `top_impacted_paths.csv`
- `network_markers.csv`

推荐图片：

## 5. 中断传播逻辑的最终展示口径

### 5.1 总体原则

中断传播的最终展示必须回答 4 个问题：

1. 冲击从哪里开始。
2. 冲击沿哪条链路传播。
3. 冲击传播到了哪些层级。
4. 冲击最终造成了多大的业务影响。

前端展示时，应把“传播链路”与“业务后果”分开表达：

- 传播链路强调路径、层级、时间推进。
- 业务后果强调服务水平、履约、积压、损失。

展示顺序建议固定为：

1. 供应商层起点
2. 原始供给层冲击
3. 有效供给/BOM 层扩散
4. 产品与系统层结果

### 5.2 供应传播

供应传播是整个中断故事的主干，应分成四层理解。

#### 5.2.1 供应商层

这层回答的是：

- 哪些 supplier 被场景直接打中。
- 哪些 supplier 因网络传播被波及。

这层的展示重点是“源头”和“扩散范围”，不是直接展示业务损失。推荐指标：

- `supplier_disrupted_nodes`
- `supplier_degraded_nodes`
- `disrupted_suppliers`
- `degraded_suppliers`

推荐展示形式：

- 趋势图：展示每天 supplier disrupted / degraded 数量。
- 快照图：在 `t_start` 和 `t_supply_peak` 看 supplier 网络哪些节点变红、变黄。

业务解释口径：

- `disrupted` 表示供应商无法正常供给。
- `degraded` 表示供应商仍可供给，但能力或稳定性下降。

#### 5.2.2 原始供给层

这层回答的是：

- 某个 item 从“直接来料”角度看，今天还能不能拿到料。

这层不考虑恢复策略最终是否已经把问题兜住，而是看原始供给冲击本身。推荐指标：

- `supply_degraded_items`
- `supply_unavailable_items`

推荐展示形式：

- 趋势图：展示原始供给受影响 item 数量随时间变化。
- `t_supply_peak` 快照：作为“原始供应冲击最重”的观察点。

业务解释口径：

- 这层体现的是“冲击本体”。
- 这层非常适合解释 `SID0003 -> MID0007 -> MID0022 -> MID0006` 这种原始供给冲击链。
- 这层不等于最终业务损伤，因为后面还有备供、替代、维修等恢复动作。

#### 5.2.3 有效供给 / BOM 层

这层回答的是：

- 在考虑主供、备供、替代、BOM 子件关系之后，item / assembly / product 最终还能不能继续供给。

推荐指标：

- `supply_effective_degraded_items`
- `supply_effective_unavailable_items`
- `material_affected_nodes`
- `material_blocked_nodes`
- `assembly_affected_nodes`
- `assembly_blocked_nodes`
- `product_affected_nodes`
- `product_blocked_nodes`

推荐展示形式：

- 物料网络趋势图：看 material / assembly / product 三层的受影响与阻断。
- 网络快照：看 `t_supply_peak` 到 `t_policy_start` 之间哪些节点仍然处于可见影响状态。

业务解释口径：

- 原始供给层强调“有没有直接来料问题”。
- 有效供给层强调“即使有来料问题，系统最终还能不能把它消化掉”。
- 这层是连接“传播过程”和“恢复效果”的桥梁层。

#### 5.2.4 产品与系统层

这层回答的是：

- 最终产品有没有受到影响。
- 整个系统是否已经进入业务受损状态。

推荐指标：

- `final_product_status`
- `system_service_level`
- `affected_days`
- `failed_days`
- `supply_affected_products`
- `supply_failed_products`

推荐展示形式：

- 核心指标趋势图。
- `t_recovery` 快照。

业务解释口径：

- 这是最终业务面。
- 前端默认“恢复”应以这层和需求层的恢复为主，而不是以原始供给节点全部清零为主。

### 5.3 贝叶斯传播

当前贝叶斯模型只用于**供应传播**，不用在需求传播上。

当前展示口径下，贝叶斯传播模型有 5 个关键约束：

1. 场景本身是外生事实。
2. 贝叶斯只负责传播，不决定场景是否发生。
3. 传播沿供应商网络**有向**进行。
4. 每天最多传播**一跳**。
5. 传播概率由 source 状态、场景严重度、target 韧性共同驱动。

当前模型的直观解释：

- 距离 0：场景直击 supplier。
- 距离 1：当天传播到的一跳下游 supplier。
- 距离 2：下一天再由距离 1 往下游继续传播。

推荐文案口径：

- 不说“全网自动扩散”。
- 要说“沿供应商依赖关系逐日有向扩散”。

推荐展示方式：

- 在 `t_start`、`t_supply_peak` 两张网络快照旁边，明确标注“冲击从距离 0 向距离 1 / 2 扩散”。
- 在说明文字中强调：
  - `disrupted > degraded`
  - `severity` 越高传播越容易
  - `compliance_rate / qms_rate / default_rate` 越差，越容易被传播打中

### 5.4 关键路径展示

路径图不是总量图，而是“传播路线图”。

推荐用于回答：

- 冲击从哪一条物料 / 装配链真正传到了最终产品。
- 哪条链是供应影响主路径。
- 哪条链是需求积压主路径。

推荐展示原则：

- `bom_impact_paths.png` 重点展示“路”，不负责展示总量。
- 图中路径应允许区分 `supply / demand / fusion` 三类影响。
- 页面文案必须明确：路径图是“代表性关键路径”，不是全量路径汇总。

## 6. 需求传播逻辑的最终展示口径

### 6.1 总体原则

需求传播不使用贝叶斯。

需求传播不是“像供应中断一样在网络里概率扩散”，而是“最终产品需求沿 BOM 自上而下分解，并把未满足需求继续向下传导”。

### 6.2 需求传播步骤

当前最终展示口径应把需求传播理解为以下 5 步：

1. 最终产品生成 `requested_demand`。
2. 根据产品当天状态计算 `fulfilled_demand`。
3. 未满足部分拆成 `backlog_demand` 与 `lost_demand`。
4. 按 BOM 用量关系从父件向子件传导。
5. 若替代已激活，则把原件未满足需求转移给替代料。

推荐指标：

- `requested_demand`
- `fulfilled_demand`
- `backlog_demand`
- `lost_demand`
- `demand_fulfillment_rate`

### 6.3 页面展示重点

页面上不要把需求传播讲成“需求节点被贝叶斯打中”，而应讲成：

- 最终产品履约下降。
- 未履约部分形成 backlog / lost。
- backlog / lost 沿 BOM 继续向下分配到子件。

推荐展示形式：

- 核心指标图中单独画 `demand_fulfillment_rate`、`total_backlog_demand`、`total_lost_demand`。
- 需要时再用表格解释某个产品把多少未满足需求向下分摊到了哪些子件。

### 6.4 与供应传播的边界

前端文案必须明确区分：

- 供应传播：解释“为什么供不上”。
- 需求传播：解释“供不上之后，哪些需求没有被满足”。

不能把这两条链混成同一种“传播”。

## 7. 恢复策略的最终展示口径

### 7.1 总体原则

恢复策略展示必须回答 4 个问题：

1. 策略何时被计划。
2. 策略何时真正生效。
3. 策略作用在谁身上。
4. 策略生效后，业务是否明显改善。

恢复策略页面应把“策略动作”和“恢复结果”分开：

- 策略动作：看 `policy_events.csv`
- 恢复结果：看 `time_series.csv`、`network_markers.csv`、网络快照

### 7.2 备供切换

备供切换的展示重点：

- 目标 item 是什么。
- backup supplier 是谁。
- 计划日期与激活日期。
- 激活后的 `capacity_factor`。
- 累计成本。

推荐前端组件：

- 时间线：显示 scheduled / activated。
- 详情表：显示 `item_id / supplier_id / capacity_factor / cost`。

业务解释口径：

- 备供切换不是“立即恢复”，而是“在切换时滞后，逐步提供替代供给能力”。
- 如果业务在 `t_policy_start` 之后很快恢复，需要说明到底是备供切换起作用，还是维修先起作用。

### 7.3 等效替代

等效替代的展示重点：

- 原物料是什么。
- 替代料是什么。
- 计划日期与激活日期。
- 替代转移量。
- 累计成本。

推荐前端组件：

- 关系对照表：原物料 -> 替代料。
- 时间线：显示替代何时真正激活。

业务解释口径：

- 替代不是简单“把原件换掉”。
- 替代应被解释为：原件供给不足时，把一部分未满足需求转移给等效料。

### 7.4 优先维修

优先维修的展示重点：

- 修复对象是 supplier 还是 item。
- 计划日期。
- 生效日期。
- 优先规则。
- 累计成本。

推荐前端组件：

- 事件时间线。
- 修复对象清单。

业务解释口径：

- 优先维修通常是“直接缩短冲击持续时间”的关键手段。
- 若 `t_policy_start` 与 `t_recovery` 接近，应重点说明是否是 priority repair 触发了恢复。

### 7.5 恢复效果应看哪些层

恢复效果不应只看原始供给是否完全清零，而要重点看：

- 有效供给层
- 融合层
- 产品层
- 需求层

推荐观察指标：

- `system_service_level`
- `demand_fulfillment_rate`
- `supply_effective_degraded_items`
- `supply_effective_unavailable_items`
- `fused_affected_items`
- `fused_failed_items`
- `total_backlog_demand`
- `total_lost_demand`
- `final_product_status`

前端解释原则：

- 恢复不是“所有 raw supplier/item 都回到 available”。
- 恢复是“业务层面已经恢复可接受状态”。

### 7.6 恢复策略的最终展示形式

恢复策略页面建议固定包含以下 4 块：

1. 策略概览卡
   - 各策略激活次数
   - 各策略累计成本
2. 事件时间线
   - scheduled / activated
3. `t_policy_start` 快照
   - 看恢复开始时网络还坏到什么程度
4. `t_recovery` 快照
   - 看恢复完成时业务与网络状态

## 8. 关键时间点的解释

### 8.1 `t0`

- 冲击前基线快照。
- 用于展示网络在场景发生前的稳定状态。
- 作用是建立“冲击前”和“冲击后”的对照基线。

### 8.2 `t_start`

- 首次可见冲击日。
- 不强制等于场景配置开始日。
- 以网络或业务指标首次出现可观察扰动为准。

它适合回答的问题是：

- 冲击从什么时候开始在图上可见。
- 第一张“出问题的网络图”应该放哪一天。

### 8.3 `t_supply_peak`

- 原始供应冲击峰值。
- 用于展示 raw supply 侧最重的一天。

推荐依据：

- `disrupted_suppliers`
- `degraded_suppliers`
- `supply_unavailable_items`
- `supply_degraded_items`

它适合回答的问题是：

- 哪一天原始供给冲击最强。
- 冲击的主峰值是在 supplier 层，还是已经传到了 item 层。

### 8.4 `t_policy_start`

- 恢复策略开始执行观察点。
- 重点看恢复措施何时第一次真正进入 `active` 状态。

典型依据包括：

- `active_backup_switches > 0`
- `active_substitutions > 0`
- `active_priority_repairs > 0`

它适合回答的问题是：

- 系统什么时候开始“真正救火”。
- 恢复是由哪一类策略首先启动的。

### 8.5 `t_recovery`

- 业务恢复观察点。
- 当前口径强调“业务已经恢复”，而不是“全网络所有节点都已经彻底清零”。

典型依据包括：

- `final_product_status == active`
- `system_service_level >= 0.999`
- `demand_fulfillment_rate >= 0.999`
- `total_backlog_demand == 0`
- `total_lost_demand == 0`

它适合回答的问题是：

- 用户面 / 业务面什么时候真正恢复。
- 从 `t_policy_start` 到 `t_recovery` 之间恢复用了多久。

### 8.6 `ttr_days`

- 业务恢复时间。
- 当前口径按最终产品恢复来统计。
- 它是首页 KPI，不是网络完全清零时间。

## 9. 前端实现建议

前端实现时建议采用以下原则：

- 所有表格、图表、指标卡优先从 `tables/frontend/*.csv` 读取
- 只把 `artifact_paths.csv` 作为图片路径和补充产物索引
- 图片仍按静态资源展示
- 不直接解析兼容性 `JSON` 或 Python 内部状态
- 页面文案必须明确区分：
  - 原始供给影响
  - 有效供给影响
  - 需求影响
  - 融合后的最终业务影响

## 10. 当前结论

当前项目已经具备：

- 后端仿真计算
- 原始表与汇总表 CSV 导出
- 前端专用 CSV 接口导出
- 图表与快照导出

后续如果继续扩展前端，应该保持：

- 页面只消费 `tables/frontend/*.csv`
- 页面样式与展示逻辑独立演进
- 后端只负责保证导出字段和业务口径稳定

## 附录：五个共享网络标记点

当前前端与报告统一使用 5 个共享网络标记点：

- `t0`
  - 冲击前基线
- `t_start`
  - 首次可见冲击
- `t_supply_peak`
  - 原始供应冲击峰值
  - 主要依据 `disrupted_suppliers`、`degraded_suppliers`、`supply_unavailable_items`、`supply_degraded_items`
- `t_policy_start`
  - 恢复策略开始执行
  - 主要依据 `active_backup_switches`、`active_substitutions`、`active_priority_repairs`
- `t_recovery`
  - 业务恢复
  - 主要依据 `final_product_status == active`、`system_service_level >= 0.999`、`demand_fulfillment_rate >= 0.999`、`total_backlog_demand == 0`、`total_lost_demand == 0`

展示解释上应明确区分：

- `t_supply_peak` 看原始供应冲击最重的时点
- `t_policy_start` 看恢复策略第一次真正进入执行状态的时点
