# 中断传播与恢复展示规范

## 1. 目标

本文档用于统一当前项目在 Web 前端、图表导出、汇报说明和后续展示整理中的展示口径，确保：

- 当前主代码只采用贝叶斯供应传播模式，不再保留确定性模式口径。
- 前端与后端完全分离，前端只消费稳定的 CSV 展示契约与 PNG 图像产物。
- 中断传播与恢复策略分开叙述，但又能通过统一的时间标记点串联成完整故事。
- 随机场景与关键节点场景的目标选择、传播解释、恢复解释、图表说明一致且可审计。

---

## 2. 前后端分离原则

### 2.1 基本原则

- 后端负责读取 `Input_data`、标准化、建模、仿真、汇总、导出。
- 前端不直接调用 Python 对象、内部状态树或临时内存对象。
- 前端展示数据只读取 `tables/frontend/*.csv`；PNG 图像等静态资源路径也必须通过前端 CSV 契约提供，其中通用图片路径索引由 `tables/frontend/artifact_paths.csv` 提供，网络快照清单由 `tables/frontend/network_snapshots.csv` 提供。
- `tables/*.csv` 属于后端分析输出；`tables/frontend/*.csv` 属于前端展示输出。前端页面不读取后端分析层 CSV，不依赖 Python 内存对象，不自行推导隐藏字段。
- 当前正式展示模式只保留贝叶斯传播，不再提供确定性模式切换入口。

### 2.2 当前前端契约

当前正式展示契约只对应两个正式目录：`output\run_random_distributed` 与 `output\run_keynode_distributed`。前端展示契约固定为：

- `tables/frontend/scenario.csv`
- `tables/frontend/summary.csv`
- `tables/frontend/kpis.csv`
- `tables/frontend/policy_start_snapshot.csv`
- `tables/frontend/time_series.csv`
- `tables/frontend/network_time_series.csv`
- `tables/frontend/network_markers.csv`
- `tables/frontend/network_snapshots.csv`
- `tables/frontend/top_impacted_paths.csv`
- `tables/frontend/policy_events.csv`
- `tables/frontend/policy_comparison_summary.csv`
- `tables/frontend/policy_comparison_time_series.csv`
- `tables/frontend/parameter_experiment_summary.csv`
- `tables/frontend/parameter_sensitivity_ranking.csv`
- `tables/frontend/artifact_paths.csv`
- `tables/frontend/manifest.csv`

其中：

- `scenario.csv`：场景定义与目标说明。
- `summary.csv`：单次运行的一行汇总。
- `kpis.csv`：首屏 KPI 卡片。
- `policy_start_snapshot.csv`：`t_policy_start` 当天的关键指标快照。
- `time_series.csv`：业务、供给、需求、恢复动作的日级时间序列。
- `network_time_series.csv`：网络节点和边的日级统计序列。
- `network_markers.csv`：五个统一 marker。
- `network_snapshots.csv`：网络快照清单，逐张列出快照标识、中文标题、日期和图片路径。
- `top_impacted_paths.csv`：代表性关键影响路径。
- `policy_events.csv`：恢复策略时间线。
- `policy_comparison_summary.csv`：不同恢复策略组合的汇总对比表，包含 `policy_profile` 编码和 `policy_label` 中文策略名称。
- `policy_comparison_time_series.csv`：不同恢复策略组合下中断节点数的日级对比时间序列，是 `policy_comparison.png` 的直接数据底表，并包含 `policy_label` 供前端直接展示中文图例。
- `parameter_experiment_summary.csv`：参数扰动分析的正式结果表。
- `parameter_sensitivity_ranking.csv`：参数对恢复效果的综合敏感度排序。
- `artifact_paths.csv`：前端需要展示的通用 PNG 图像路径索引，只保留前端实际展示所需的图片路径；每条路径必须逐行展开，不能把多张图片路径以列表字符串写入单个单元格。
- `manifest.csv`：前端数据清单。

前端默认展示不依赖 `history.csv`、`item_history.csv`、`network_history.csv` 等审计级表。这些表只作为后端复核或分析下钻使用。

## 3. 当前正式实验情境与场景

当前正式实验只保留两种情境、两个正式场景。

### 3.1 随机中断情境

正式场景：

- `default_random_distributed_node_disruption`

含义：

- 固定随机种子。
- 从非关键普通节点中抽取 3 到 5 个节点。
- 节点分布在不同链段和不同层级。
- 节点同时中断。

当前实现口径：

- 固定随机种子为 `42`。
- 默认抽取 4 个节点：
  - 2 个普通供应商节点
  - 2 个普通物料/装配节点
- 供应商节点从“与最终产品相关、但不属于高影响关键集合”的当前供给节点中选择。
- 物料节点从“与最终产品相关、但非关键、非关键物料”的祖先物料/装配节点中选择。
- 选择算法优先保证层级差异和支路差异，避免都落在同一局部支路上。

### 3.2 关键节点中断情境

正式场景：

- `default_keynode_distributed_disruption`

含义：

- `Input_data/keynodes` 目录下关键供应商清单中 `is_critical=1` 的供应商同时中断。
- 该场景用于观察显式关键节点集中受损下的系统性传播与协同恢复规律。

当前实现口径：

- 目标集合由 `AUTO_KEY_SUPPLIERS` 自动解析。
- 关键节点只来源于 `Input_data/keynodes/monthly_v2_bom_rankings_by_month.csv` 和 `Input_data/keynodes/monthly_v2_supplier_rankings_by_month.csv` 两份清单。
- 解析对象为供应商清单中 `is_critical=1` 的供应商；当前数据下会解析出 14 个关键供应商。

### 3.3 正式输出目录

- 随机中断情境固定回写到 `output\run_random_distributed`。
- 关键节点中断情境固定回写到 `output\run_keynode_distributed`。

## 4. 统一的时间标记点

当前所有场景、所有图表和前端页面统一使用 5 个 marker。

- `t0`：冲击前基线。
- `t_start`：首次可见冲击。
- `t_supply_peak`：原始供应冲击峰值。
- `t_policy_start`：恢复策略开始生效。
- `t_recovery`：业务恢复。

### 4.1 `t0`

含义：

- 场景开始前一天的基线网络状态。
- 用于和后续冲击状态做前后对比。

### 4.2 `t_start`

含义：

- 第一天出现可见中断或受影响迹象的时间点。

展示口径：

- 不要求严格等于配置中的开始日期。
- 更强调“图上第一次看得见变化”的日期。

### 4.3 `t_supply_peak`

含义：

- 原始供应冲击最重的时间点。

主要依据：

- `disrupted_suppliers`
- `degraded_suppliers`
- `supply_unavailable_items`
- `supply_degraded_items`

说明：

- 这是“冲击本体”的峰值，不是“最终业务影响”的峰值。

### 4.4 `t_policy_start`

含义：

- 恢复策略第一次真正进入生效状态的时间点。

主要依据：

- `active_backup_switches > 0`
- `active_substitutions > 0`
- `active_priority_repairs > 0`

说明：

- 这里回答的是“系统什么时候真正开始救火”，不是“什么时候已经恢复”。

### 4.5 `t_recovery`

含义：

- 业务恢复时间点。

当前判据：

- `final_product_status == active`
- `system_service_level >= 0.999`
- `demand_fulfillment_rate >= 0.999`
- `total_backlog_demand == 0`
- `total_lost_demand == 0`

说明：

- 这里看的是业务恢复，而不是全网络所有原始节点都恢复到零风险状态。

## 5. 中断传播的最终展现形式与逻辑

### 5.1 总体叙述顺序

中断传播必须按以下顺序解释：

1. 冲击从哪里开始。
2. 冲击沿哪类依赖关系扩散。
3. 冲击传到了哪些层级。
4. 冲击最终造成了多大的业务后果。

前端和文档必须把中断传播拆成 4 层：

1. 供应商层
2. 原始供给层
3. 有效供给 / 物料清单层
4. 产品与系统层

### 5.2 供应商层

这一层回答：

- 哪些供应商被场景直接打中。
- 哪些供应商因贝叶斯传播被波及。

推荐指标：

- `supplier_disrupted_nodes`
- `supplier_degraded_nodes`
- `disrupted_suppliers`
- `degraded_suppliers`

推荐图：

- `supplier_network_trends.png`
- `t_start_network.png`
- `t_supply_peak_network.png`

### 5.3 原始供给层

这一层回答：

- 哪些 item 在“不考虑恢复兜底”时已经直接供不上。

推荐指标：

- `supply_degraded_items`
- `supply_unavailable_items`

推荐图：

- `core_metric_trends.png`
- `demand_propagation_trends.png`
- `t_supply_peak_network.png`

### 5.4 有效供给 / 物料清单层

这一层回答：

- 在考虑备供、替代、物料清单子件状态之后，哪些物料、装配、产品仍然受影响或被阻断。

推荐指标：

- `supply_effective_degraded_items`
- `supply_effective_unavailable_items`
- `material_affected_nodes`
- `material_blocked_nodes`
- `assembly_affected_nodes`
- `assembly_blocked_nodes`
- `product_affected_nodes`
- `product_blocked_nodes`

推荐图：

- `material_network_trends.png`
- `bom_impact_paths.png`

### 5.5 产品与系统层

这一层回答：

- 最终产品是否受影响。
- 系统服务水平是否下降。
- 是否产生积压需求和损失需求。

推荐指标：

- `final_product_status`
- `system_service_level`
- `demand_fulfillment_rate`
- `total_backlog_demand`
- `total_lost_demand`

推荐图：

- `core_metric_trends.png`
- `demand_propagation_trends.png`

### 5.6 贝叶斯传播的展示口径

当前项目中，贝叶斯只用于**供应传播**，不用于需求传播。

当前贝叶斯传播口径必须统一表述为：

- 场景是否发生由外生场景决定，不由贝叶斯决定。
- 贝叶斯只负责供应商到供应商的传播。
- 传播沿供应商网络**有向**进行。
- 每天最多传播**一跳**。
- 传播概率由 `source 状态 + severity + target 韧性` 共同决定。

前端和文档中不要再使用“确定性模式”对照口径。

### 5.7 需求传播的展示口径

需求传播不是贝叶斯扩散，而是：

- 最终产品需求生成。
- 未满足需求形成积压需求或损失需求。
- 积压需求和损失需求按物料清单用量自上而下分解。
- 若替代已经激活，则未满足需求可以转移到替代料。

因此文档和页面中必须明确区分：

- 供应传播：解释“为什么供不上”
- 需求传播：解释“供不上以后哪些需求没有被满足”

推荐图：

- `demand_propagation_trends.png`

## 6. 恢复策略的最终展现形式与逻辑

### 6.1 恢复策略展示原则

恢复策略页面必须回答：

1. 策略何时计划。
2. 策略何时生效。
3. 策略作用于谁。
4. 策略生效后是否推动业务恢复。

必须分开叙述：

- 策略动作本身
- 恢复结果本身

### 6.2 三类恢复策略

当前展示应覆盖 3 类策略：

- 备供切换
- 等效替代
- 优先维修

### 6.3 策略动作的展示

核心数据源：

- `policy_events.csv`

需要展示的字段含义：

- `policy_type`
- `action`
- `target_id`
- `target_type`
- `date`
- `cost`
- `metadata`

推荐展示方式：

- 时间线
- 事件表
- 成本卡片
- `timeline_overview.png`

### 6.4 恢复结果的展示

恢复结果不能只看原始供应商或物料状态是否全部清零，而要重点看：

- 有效供给层
- 融合层
- 产品层
- 需求层

推荐指标：

- `system_service_level`
- `demand_fulfillment_rate`
- `supply_effective_degraded_items`
- `supply_effective_unavailable_items`
- `fused_affected_items`
- `fused_failed_items`
- `total_backlog_demand`
- `total_lost_demand`
- `final_product_status`

推荐图：

- `core_metric_trends.png`
- `demand_propagation_trends.png`
- `timeline_overview.png`
- `t_policy_start_network.png`
- `t_recovery_network.png`

### 6.5 `t_policy_start` 到 `t_recovery` 的解释

文档和页面都应明确解释：

- `t_policy_start`：系统开始真正动用恢复策略。
- `t_recovery`：业务已经恢复。

这两个点之间的时间差，描述的是：

- 从开始止损到业务恢复总共用了多久。

### 6.6 策略对比图

当恢复策略章节需要回答“哪一类策略更快压住中断节点”时，必须补充策略对比图。

正式单场景图：

- `policy_comparison.png`

正式统计底表：

- `policy_comparison_time_series.csv`

正式口径：

- 固定同一情境，比较 `baseline`、`all_policies`、`no_policy`、`only_backup_switch`、`only_substitution`、`only_priority_repair` 六类策略组合。
- `baseline` 表示“不额外覆写任何策略开关”，直接使用 `load_default_policies()` 从 `default_params.yaml` 读取的当前默认策略配置。
- `all_policies` 表示显式将备用切换、等效替代、优先修复三类恢复策略全部置为启用，主要用于做显式全策略对照。
- 当前 `default_params.yaml` 中三类恢复策略均为 `enabled: true`，因此在现有配置下，`baseline` 与 `all_policies` 的运行结果会重合。

- 图中主指标统一采用中断节点数时间序列，不再使用单场景的多指标条形图。
- 正式折线图重点展示：
  - `supplier_disrupted_nodes`
  - `material_blocked_nodes`
  - `assembly_blocked_nodes`
  - `product_blocked_nodes`
  - `downstream_interrupted_nodes`
  - `total_interrupted_nodes`
- 该图回答的是“哪种策略更快压住传播尾部并减少中断节点”，适合放在恢复策略展示主区域中。

## 7. 不同情境下的中断传播与恢复策略展示

### 7.1 随机中断情境：随机普通节点分散中断

正式场景：

- `default_random_distributed_node_disruption`

### 7.1.1 场景定义

该场景用于表达：

- 中断没有优先打击主干关键节点。
- 中断以分散、离散、局部叠加的方式出现。
- 冲击首先表现为局部供给缺口和局部链段受限。

当前实现中，这个场景固定随机种子，选择 3 到 5 个普通节点，节点同时中断，且优先分布到不同层级和不同支路。

### 7.1.2 中断传播部分应如何展示

这一情境下，中断传播的最终展现重点不是“主干系统被瞬间击穿”，而是：

- 局部异常如何被识别。
- 哪些局部供应商或物料先出现中断。
- 局部异常有没有进一步扩散到装配和产品层。
- 扩散是否被局部吸收。

推荐重点图表：

- `supplier_network_trends.png`
- `material_network_trends.png`
- `monthly_disrupted_nodes.png`
- `bom_impact_paths.png`
- `demand_propagation_trends.png`
- `t_start_network.png`
- `t_supply_peak_network.png`

推荐叙述逻辑：

1. 先说明这几个普通节点是如何被固定随机种子选出的。
2. 再看这些普通节点的中断是否真的沿供应链扩散。
3. 再看冲击是否仍被限制在局部支路。
4. 最后解释是否形成了明显的产品和系统服务影响。

页面文案必须强调：

- 这是分散式局部冲击。
- 重点不是关键主干断裂，而是局部风险的扩散与吸收。

### 7.1.3 恢复策略部分应如何展示

这一情境下，恢复策略的重点应放在：

- 局部修补是否及时。
- 局部补位是否有效。
- 是否成功阻止局部异常向外扩散。

推荐重点图表和数据：

- `policy_events.csv`
- `policy_start_snapshot.csv`
- `timeline_overview.png`
- `core_metric_trends.png`
- `policy_comparison.png`
- `policy_comparison_time_series.csv`
- `parameter_experiment_summary.csv`
- `parameter_sensitivity_ranking.csv`
- `parameter_sensitivity_ranking.png`
- `t_policy_start_network.png`
- `t_recovery_network.png`

推荐叙述逻辑：

1. 说明哪类策略最先开始生效。
2. 说明策略生效后，局部中断是否被压回局部范围。
3. 说明从 `t_policy_start` 到 `t_recovery` 的恢复节奏。
4. 说明局部场景下哪类策略更像“快速缝补”，并用中断节点对比折线图说明其压制速度。
5. 说明参数扰动分析表明，局部场景下备份覆盖率和修复提前期比替代可得性更敏感。

页面文案必须强调：

- 随机分散冲击的快速响应重点是“快发现、快止损、快修补”。

### 7.2 关键节点中断情境：清单关键供应商同时中断

正式场景：

- `default_keynode_distributed_disruption`

### 7.2.1 场景定义

该场景用于表达：

- 中断优先打在清单中明确标记为关键的供应商节点上。
- 冲击更容易造成结构性断裂和系统性压力。
- 恢复重点从“局部修补”转向“保障关键功能连续”和“跨主体协同处置”。

### 7.2.2 中断传播部分应如何展示

这一情境下，中断传播的最终展现重点应放在：

- 供应商层的高强度集中冲击。
- 清单关键供应商对应的多支路同时受损。
- 冲击是否快速穿透到物料、装配和产品层。
- 传播持续时间是否明显拉长。

推荐重点图表：

- `supplier_network_trends.png`
- `material_network_trends.png`
- `monthly_disrupted_nodes.png`
- `propagation_duration_comparison.png`
- `bom_impact_paths.png`
- `demand_propagation_trends.png`
- `t_supply_peak_network.png`

推荐叙述逻辑：

1. 先说明关键供应商来自 `Input_data/keynodes` 清单中 `is_critical=1` 的节点，当前为 14 个供应商。
2. 再说明供应商层为何迅速形成高峰。
3. 再说明这种高峰如何通过多条物料清单路径向下游扩散。
4. 最后说明系统层是否出现明显的服务与履约损失。

页面文案必须强调：

- 这不是普通局部异常，而是关键路径上的系统性冲击。

### 7.2.3 恢复策略部分应如何展示

这一情境下，恢复策略的重点应放在：

- 哪些策略先启动。
- 哪些策略形成了真正的系统兜底。
- 多策略协同时，瓶颈到底在供应商修复、物料替代还是整体协同速度。

推荐重点图表和数据：

- `policy_events.csv`
- `timeline_overview.png`
- `core_metric_trends.png`
- `policy_comparison.png`
- `policy_comparison_time_series.csv`
- `parameter_experiment_summary.csv`
- `parameter_sensitivity_ranking.csv`
- `parameter_sensitivity_ranking.png`
- `monthly_disrupted_nodes.png`
- `propagation_duration_comparison.png`
- `t_policy_start_network.png`
- `t_recovery_network.png`

推荐叙述逻辑：

1. 说明面对关键路径集中中断时，单一策略通常不够。
2. 说明备供、替代、维修分别在哪些对象上发力。
3. 说明 `t_supply_peak -> t_policy_start -> t_recovery` 三段时间差。
4. 说明恢复的难点是“跨主体协同压缩系统性尾巴”。
5. 说明参数扰动分析表明，关键节点情境下备份覆盖率仍最敏感，但备供切换时滞和修复提前期对恢复尾部的影响更值得强调。

页面文案必须强调：

- 关键节点中断情境下，快速响应的重点是“优先保障关键功能连续，组织跨主体协同恢复”。

## 8. 图表作用与展示口径

当前单次运行 10 张主要图的作用如下：

- `core_metric_trends.png`
  - 看业务层是否真正受损和何时恢复。
- `demand_propagation_trends.png`
  - 看需求满足率、积压需求和损失需求是如何形成并被消化的。
- `supplier_network_trends.png`
  - 看供应商层如何扩散。
- `material_network_trends.png`
  - 看物料、装配、产品层如何被波及。
- `monthly_disrupted_nodes.png`
  - 看哪一个月最严重，严重在哪一层。
- `propagation_duration_comparison.png`
  - 看哪一层拖得最久。
- `bom_impact_paths.png`
  - 看具体是哪些路径把影响传到了最终产品。
  - 图形版式固定为物料层级单列布局：跨层关系使用直线，同层关系使用轻微弧线。
- `timeline_overview.png`
  - 看策略事件、影响峰值和业务恢复是否在统一时间轴上闭环。
- `policy_comparison.png`
  - 看同一情境下不同恢复策略如何压制中断节点总数与下游阻断节点数。
- `parameter_sensitivity_ranking.png`
  - 看哪类能力参数对恢复结果更敏感。

当前单次运行还会固定输出两张正式参数实验表：

- `parameter_experiment_summary.csv`
  - 直接用于参数扰动分析，回答不同参数取值下恢复时间、系统服务水平、损失与成本如何变化。
- `parameter_sensitivity_ranking.csv`
  - 用于解释各参数影响强弱的相对顺序。

网络快照固定为：

- `t0_network.png`
- `t_start_network.png`
- `t_supply_peak_network.png`
- `t_policy_start_network.png`
- `t_recovery_network.png`

网络快照展示口径：

- 节点类型、节点状态和边状态分别通过图例解释。
- 关键节点统一使用亮玫红色 3.0 加粗边框标识，并在节点类型图例中显示为“关键节点”。
- 网络快照采用静态单图版式：上方为物料清单网络，下方为供应商网络，中间保留清晰的映射通道。
- 物料清单网络采用分层单列布局：原材料层、零件层、装配层和最终产品层分别保持一列，并使用收紧后的横向间距，保留“原材料—零件—装配—产品”的从左到右层级关系。
- 供应商网络位于物料清单网络下方，并与物料层保持明显纵向间距；正式版式按三列组织供应商节点，左右边界与物料清单网络最左层、最右层对齐。
- 上下两部分网络围绕共同中心展开，但不强制供应商列与物料列逐列重合，以便保留供应商到物料节点的连线辨识度。
- 网络快照对应的前端图片清单必须通过 `tables/frontend/network_snapshots.csv` 提供，前端不得再从 `artifact_paths.csv` 中解析列表字符串推导快照集合。
- 关键节点高亮颜色不得与可用、降级、中断、备用、替代等状态色混淆。

趋势图展示口径：

- 右侧图例统一放在图外右侧。
- 折线末端标签用于标明最终数值，同一位置附近的多个标签必须自动错开，避免遮挡。

## 9. 正式输出约束补充

- 正式单场景结果目录只围绕 `output\run_random_distributed` 和 `output\run_keynode_distributed` 两个目录组织。
- 两个正式场景目录都会自动输出以下三张关键补充图：
  - `demand_propagation_trends.png`
  - `timeline_overview.png`
  - `policy_comparison.png`
- 两个正式场景目录还会自动输出以下参数实验产物：
  - `parameter_experiment_summary.csv`
  - `parameter_sensitivity_ranking.csv`
  - `parameter_sensitivity_ranking.png`
- 同时会输出 `policy_comparison_time_series.csv`，用于审计策略对比图的时间序列来源。
- `parameter_experiment_summary.csv` 是参数扰动分析的数据源；`parameter_sensitivity_ranking.csv` 和 `parameter_sensitivity_ranking.png` 用于辅助解释哪些能力参数更敏感。
- 其中 `policy_comparison.png` 的正式口径是：在同一情境内，基于 `policy_comparison_time_series.csv` 对 `baseline`、`all_policies`、`no_policy`、`only_backup_switch`、`only_substitution`、`only_priority_repair` 六类策略组合的中断节点数时间序列进行可视化，并将策略对比图回写到该情境自己的 `figures` 目录。

- `policy_comparison.png` 必须采用“不同恢复策略下中断节点数对比折线图”形式，不再使用单场景多指标条形图。
- `timeline_overview.png` 的双纵轴口径固定为：左轴展示动作数量，右侧蓝色刻度展示累计策略成本，具体成本序列由图例中的“累计策略成本”标识；图例必须放在右侧且与右侧刻度保留明显间距。
- 因此，单场景展示不需要依赖任何跨情境批量目录；策略对比图和对应 CSV 均由当前情境自己的输出目录直接提供。
- 传播部分的主线是“冲击从哪里开始、沿什么关系传播、最终造成什么需求后果”，恢复部分的主线是“策略何时启动、作用到哪里、是否压住传播尾部并恢复业务”，两部分不能混写，也不能重复解释同一层逻辑。
- 所有正式导出的 PNG 图中，标题、图例、坐标轴名称和注释统一使用中文；日期轴统一使用 `YYYY-MM-DD` 格式；有图例的图统一将图例放在右侧。
